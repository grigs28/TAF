# TAF 压缩管道 GIL 瓶颈与提速方案分析（含 multiprocessing 专项评估）

> 日期：2026-10-15（10/15 月度备份运行期间只读测量，未做任何修改）
> 关联文档：`docs/运维记录_NFS性能优化_20261008.md`、外部分析 `taf-tape-backup-gil.md`

## 1. 瓶颈确认（代码 + 实测双重证据）

压缩管道在 OS 层是 9 条独立流（每条：Python 打包 → 管道 → zstd 子进程），但**打包（tarfile）在主进程线程池内用纯 Python 完成**，受 GIL 约束无法真并行：

```
9 个 executor 线程: _compress_with_zstd_cli()
  └─ tarfile.open(fileobj=zstd.stdin, mode='w|')   # 纯 Python，GIL 串行
  └─ zstd -3 -T3 子进程                            # C 实现，真并行（但在等喂料）
```

实测（PID 92198，只读采样）：

| 指标 | 实测值 | 含义 |
|---|---|---|
| 主进程 CPU | 188.6%（~1.9核） | 10 个活跃线程各 16~32%，无单线程满载 —— 典型 GIL 争抢 |
| 主进程读源 | 507 MB/s | NFS 三层调优后读取已很强，不是瓶颈 |
| zstd 压缩输出 | 207 MB/s（9 进程） | 产线被喂入速度卡死 |
| zstd CPU | 229%（24 核中仅 2.3 核） | 压缩算力大量闲置 |
| 页缓存 | 61 GB | 内存不是瓶颈（70GB 机器） |
| 磁带 | LTO-9 HH 原生 300MB/s | 占空比低是“喂不饱”，非磁带慢 |

压缩产物：平均 4.05GB/块（原始组 12GB×95%，zstd -3 约 2.8:1）。当日已入带 3.3TB。

## 2. 方案全景与选择

| 方案 | 破 GIL 原理 | 改动量 | 保留逐文件错误/进度 | 跨平台 | 结论 |
|---|---|---|---|---|---|
| ① 系统 tar 子进程 | C 实现不占 GIL | 小（~40行） | ❌ 需重建（`--ignore-failed-read` 只能保不中断，失败明细采集要另做）；tar 无逐文件进度钩子，UI 进度退化为块级 | ❌ Windows 无原生 tar | 快糙猛，但要重做错误清单与 BrokenPipe 语义 |
| ② **multiprocessing 工作进程**（本文专项） | 每进程独立解释器/GIL | 中（~200-300行+测试） | ✅ 完全保留（Python 打包逻辑不动） | ✅ spawn 全平台可用 | **长期最优解** |
| ③ tar.copybufsize 调大 | 减少 Python 循环次数 | 1行（已上线 0.6.9，默认 4MB） | ✅ | ✅ | 只抬高 ~30%，不是破顶 |
| ④ Python 3.13t/3.14 free-threading | 官方无 GIL 构建 | 大（换解释器+依赖） | ✅ | ✅ | 当前 env 为 Python 3.10，不可行 |

## 3. ② multiprocessing 专项：代价与好处

### 3.1 现在的状态共享（换进程边界的全部难点）

`_compress_with_zstd_cli()` 目前跨线程共享三样东西：

1. **`backup_task` 富对象**——但实测只用到 `progress_percent` 和
   `current_compression_progress` 两个标量属性（compressor.py:854-924），
   用轻量 shim（dict/简单对象）即可，**无需 pickle 整个任务对象**。
2. **`compress_progress` 共享字典**——worker 直接改写、主进程 UI 读取。
   跨进程必须换成 **进度事件队列**（`multiprocessing.Queue` + 父进程泵任务），
   这是最大的结构性改动。
3. **结果返回值**（成功/失败文件清单、大小）——本身可 pickle，天然适配。

### 3.2 好处

- **真并行**：9 个 worker 进程各有独立 GIL，Python 打包可跑到接近 9 倍单流，
  直到撞上 NFS 聚合读（~1.9GB/s 实测）或 zstd 算力，预期压缩输出从
  ~200MB/s 提到 500-800MB/s，压缩阶段时长缩短 2-3 倍。
- **语义零回归**：tarfile 逐文件 try/except 原样保留——失败文件清单
  （0.6.3 加的入库功能）、BrokenPipe 即停（0.6.5 加的）、逐文件进度
  （UI 精细到当前第 N 个文件）全部不动。这是相对 ① 的决定性优势。
- **跨平台**：spawn 在 Windows 同样可用，符合项目双平台定位（① 在 Windows 不可行）。
- **故障隔离**：worker 崩溃只影响一组，可重试/报告；内存泄漏随组回收。
- **资源富裕可兑现**：24 核/70GB 当前 80% 空闲，正好多进程吃下。

### 3.3 代价（按工作量排序）

| 项 | 内容 | 估计 |
|---|---|---|
| 进度事件通道 | worker 用 Queue 发 `{group_idx, file_idx, bytes, ...}`，父进程泵任务更新 compress_progress 与 backup_task 标量 | ~60 行 |
| 池生命周期 | spawn 上下文建池（**必须 spawn 不能 fork**：主进程已有 DB 连接/事件循环，fork 继承套接字会出事）；备份开始建、结束/取消时销毁 | ~50 行 |
| 取消与 BrokenPipe | 取消任务 → terminate 池；worker 内 zstd 子进程要用进程组/setsid 确保一起被杀，不能留孤儿 | ~30 行 |
| worker 入口 | 模块级函数包一层（spawn 要求可 pickle 入口），参数瘦身：路径+大小列表、归档路径、级别、线程数、组索引 | ~30 行 |
| 日志 | spawn 后 handler 不继承：QueueHandler→主进程 QueueListener 集中写日志（或先接受 worker 日志简化输出） | ~40 行 |
| 测试 | 小数据集→失败注入→取消测试→长跑稳定性→Windows spawn 路径 | 约 1 天 |

**合计：约 200-300 行新增/修改 + 1-2 天含测试，对比 ① 约 40 行 + 半天。**

### 3.4 风险清单（实施时的验收点）

- [ ] spawn 池在备份任务开始时创建，绝不 fork 已有连接的进程
- [ ] zstd 孙进程随 worker 一并终止（进程组），取消测试必须看到无残留 `pgrep zstd`
- [ ] 失败文件清单与错误原因逐字一致地回到主进程（含超长文件名用例）
- [ ] 进度更新节流（事件合批，避免 Queue 成为新瓶颈：每 100 文件或 0.5s 一条）
- [ ] 池关闭后 `final/` 搬运与 tape 流程与现状一致（结果结构不变）
- [ ] Windows 路径走通（spawn + `if __name__ == '__main__'` 保护）

## 4. 建议路线

1. **已做**：NFS 三层调优（读 364MB/s→1.1GB/s）+ `COMPRESSION_TAR_COPYBUF_MB=4`（0.6.9）。
2. **若追求最快上线、可接受块级进度和重做失败清单** → 方案 ①（系统 tar）。
3. **若要保留逐文件进度/错误语义、跨平台、长期架构干净** → 方案 ②（本评估推荐）。
4. ① 与 ② 不互斥：可先 ③（已上）观察 10/15 本次运行数据，再决定投入。

## 5. 关键代码位置

- 打包函数：`backup/compressor.py:_compress_with_zstd_cli()`（模块级，利于 spawn pickle）
- 线程池入口：`backup/compressor.py:1808 loop.run_in_executor(None, _do_7z_compress)`
- 共享进度：`backup_task.progress_percent` / `current_compression_progress`（:854-924）
- 并行度：`COMPRESSION_PARALLEL_BATCHES=9`（扫描期 -1=8），`zstd -3 -T3`
